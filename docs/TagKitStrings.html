TagKitStrings

How TagKit's own words get translated.

#include "tagkit/TagKitStrings.h"

Detailed Description

TagKit's own words — column titles, field names, buttons, window titles, the “(multiple)” shown for files that disagree — are English by default, and nothing needs any library for that. A program that has a Haiku catalog (a Locale Kit one) defines TAGKIT_USE_CATALOG when it builds, in DEFINES next to the TAGKIT_CLIENT_* ones:

DEFINES = TAGKIT_CLIENT_NAME=MyApp TAGKIT_CLIENT_VERSION=1.0 \
	TAGKIT_USE_CATALOG
LIBS = $(STDCPPLIBS) be $(TAGKIT_LIBS) $(TAGKIT_CATALOG_LIBS)

(TAGKIT_CATALOG_LIBS is localestub, the static library every program that uses B_TRANSLATE links; without it the link fails with undefined references to BLocaleRoster::GetCatalog().)

Every string in TagKit then goes through B_TRANSLATE_CONTEXT() with the context "TagKit":

  • The program's own catalog is searched for them at run time, so there is nothing to set up in the code; only the catalog.
  • Haiku's catkeys collection (make catkeys) finds them in TagKit's source files just as it does the program's own, because TagKit is compiled into the program. They land in the program's .catkeys file under the context TagKit.
  • A string without a translation is shown in English.

Words a program gives TagKit itself, such as an EmptyArtButton's label, are the program's to translate. The genre names are not translated, and neither are the audio format names.

Messages with something in them have a %placeholder% replaced with the value after translating (“Edit %field%”, “Cover art for "%file%"”), and counts use ICU plural rules ({0, plural, one{# file selected} other{# files selected}}), which a translator can adapt to the language's own plural forms.

Using the program's own words

A program that already translates the same words (ArmyKnife has its own “Artist”, “Album” and so on, in its own catalog contexts) can have TagKit show those, or different wording, by installing an override once at start-up, before any TagKit window or view is made:

static const char*
MyStrings(const char* english, const char* translated, void* cookie)
{
	if (strcmp(english, "Artist") == 0)
		return B_TRANSLATE_CONTEXT("Artist", "EditorView");
	if (strcmp(english, "Album") == 0)
		return B_TRANSLATE_CONTEXT("Album", "EditorView");
	return NULL;	// keep TagKit's own
}

tagkit::set_string_override(MyStrings);

The function is called for every TagKit string with the English text as written in TagKit's source and what TagKit would show; it returns the text to show instead, or NULL to keep it. The pointer is not copied, so it must stay valid, which is true of what B_TRANSLATE() returns. Because the B_TRANSLATE_CONTEXT() calls are in the program's own source, the program's catkeys collection finds them. It works with or without TAGKIT_USE_CATALOG. The plural text for files_selected_text() is also passed through (its English is the whole {0, plural, ...} pattern) but only when TAGKIT_USE_CATALOG is defined.

TAGKIT_TR(text)

Marks and translates a string.

With TAGKIT_USE_CATALOG it is B_TRANSLATE_CONTEXT(text, "TagKit"); without it, just the text; either way the result goes through the override, if one is set. Call it where the string is used, not for a global or static, so the translation is looked up after the program's catalog is loaded.
